  and `git ls-remote --heads URL` both list 265 heads. Found when the first
  end-to-end run reported no channel.
- nixpkgs release tags are annotated: `refs/tags/26.05` is `76b7bc9…` (the
  tag object) and `refs/tags/26.05^{}` is `8c50a71…` (the commit). A lock must
  pin the commit.

## Design (debated)

| Option | Verdict |
|---|---|
| Edit `flake.lock` by hand | Rejected: error-prone, and the repo's own tools should do it. |
| `nix flake update` | Blocked here (tarballs). |
| `nix flake lock --override-input nixpkgs git+https://…` | Rejected: it writes a git-type lock entry, changing the lock type for every user, and `parse_lock` handles only github entries. |
| **`nix_git_inputs.update_input`**: resolve the ref with `git ls-remote`, fetch over git, write an ordinary `github` entry | **Chosen.** Git and tarball fetches of a revision have the same `narHash`; the existing override verification already relies on that. |

`scripts/update_nixos_stable.py` (the documented tool) now:
- discovers channels and tags with `git ls-remote` instead of the REST API;
- updates the lock through `update_input`.

That leaves one update path, which works on every host.

## Design (debated)

| Option | Verdict |
|---|---|
| Edit `flake.lock` by hand | Rejected: error-prone, and the repo's own tools should do it. |
| `nix flake update` | Blocked here (tarballs). |
| `nix flake lock --override-input nixpkgs git+https://…` | Rejected: it writes a git-type lock entry, changing the lock type for every user, and `parse_lock` handles only github entries. |
| **`nix_git_inputs.update_input`**: resolve the ref with `git ls-remote`, fetch over git, write an ordinary `github` entry | **Chosen.** Git and tarball fetches of a revision have the same `narHash`; the existing override verification already relies on that. |

`scripts/update_nixos_stable.py` (the documented tool) now:
- discovers channels and tags with `git ls-remote` instead of the REST API;
- updates the lock through `update_input`.

That leaves one update path, which works on every host.

## Root cause of the disko failure (26.05), trbarbour/NixOS-boot-image#311

1. **What the journal showed.** In the guest, disko builds its generated
   script, `disko-destroy-format-mount`. Nix reported "780 derivations will
   be built", starting from the bootstrap seeds (`hex0`, `stage0-posix`).
   They include `make-binary-wrapper-hook`. The binary cache was
   unreachable (TLS through the sandbox), so the build failed.
2. **U1, which part needs a compiler.** On the host, with this repo's disko
   and a minimal configuration, `disko --dry-run` gives a script derivation
   (built by nixpkgs' `writers`) whose direct inputs include
   `make-binary-wrapper-hook` and `stdenv-linux`.
3. **U2, is this new in 26.05.** No.
   - The first comparison was invalid: `NIX_PATH` has no effect, because the
     disko package embeds the nixpkgs it was built with
     (`inputs.nixpkgs.follows`). Both runs gave the same output path.
   - Repeated with a disko built from `main` (25.05): the script has the
     same `make-binary-wrapper-hook` and `stdenv` inputs.
4. **What changed: the image's `system.extraDependencies`.**
   - On 25.05 it contains both `pkgs.stdenv` and `pkgs.stdenvNoCC`, so the
     guest could build the small hook locally.
   - On 26.05 it contains **only `stdenvNoCC`**.
   - Runtime closures agree: the 25.05 system has `gcc-wrapper-14.3.0` and the
     26.05 system has no `gcc-wrapper`.
   - The missing hook path, `01gh6jng…-make-binary-wrapper-hook`, is exactly
     the one the guest tried to build.
5. **Fix:** `system.extraDependencies = [ pkgs.makeBinaryWrapper ]` in
   `modules/pre-nixos.nix`.
   - A first version also added `pkgs.stdenv`. The new test showed that only
     the hook was missing; the script's stdenv is the `stdenvNoCC` already
     present. The hook's closure carries the `gcc-wrapper` it calls. So
     `pkgs.stdenv` was dropped as unnecessary.
6. **Permanent test:** `tests/vm/test_disko_offline_closure.py` (marked
   `vm`; about 1 min, no boot), with the helper `tests/vm/offline_closure.py`
   and its unit tests.
   - It builds the image's system closure and disko, dry-runs a
     planner-rendered configuration, and asserts that every input output the
     script needs is in the closure.
   - Without the fix it **fails** and names `01gh6jng…-make-binary-wrapper-hook`
     (22:55Z, 53 s). With the fix it **passes** (43 s, and 61 s for the
     minimal version).

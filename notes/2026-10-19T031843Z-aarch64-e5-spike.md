# AArch64 E5/E6 spike: booting the SD image's system under qemu-system-aarch64

AArch64 plan §6 item 7, experiments E5 (does `-M virt` boot it, and how fast
is boot to login?) and E6 (`nixos-generate-config` on non-EFI AArch64).
User decision U5: the Pi firmware/U-Boot chain need not be tested, so this
uses a direct kernel boot.

- **Artifact:** E4's SD image (0.15.0),
  `/nix/store/24ywhnjh…-nixos-image-sd-card-26.05.20261015.26f4107-aarch64-linux.img.zst`
  (1.6 GiB compressed, 3.96 GiB raw). Its system closure is
  `/nix/store/r029j6da…-nixos-system-nixos-sd-card-26.05.20261015.26f4107`.
  Its `kernel-params` are byte-identical to the user's CM4 `/proc/cmdline`:
  R-P2 holds on the built artifact.
- **Host:** `qemu-system-arm` 8.2.2, installed by hand on 2026-10-19 and not
  yet in `DEV_APT_PACKAGES`.
- **QEMU:** `-M virt -cpu cortex-a72 -smp 2 -m 2048`, `-kernel/-initrd` from
  the closure, `-append "<kernel-params> init=<closure>/init"`, the SD image as
  a writable virtio disk, an empty 4G virtio target, and `-serial stdio` (the
  PL011, seen as `ttyAMA0` in the guest).
- Script: `notes/2026-10-19T031843Z-aarch64-e5-spike/spike.py`.

## run1 (QEMU from 2026-10-19 02:41:51Z, login timeout 300 s, the default)

- The kernel booted: `Machine model: linux,dummy-virt`, `ttyAMA0 … PL011`, and
  root from the SD image. systemd reached its targets, created the
  `serial-getty` slice and logged "Expecting device /dev/ttyAMA0…". pre-nixos
  printed its version banner.
- No `login:` arrived within 300 s, by which point the guest clock had
  reached only about 123 s.

## run2 (02:47:33Z to 03:17:38Z, login timeout 1800 s, clean disks)

- Again **no login prompt in 30 minutes**. pre-nixos ran: it broadcast
  `LAN IPv4 address unavailable (preferred interface "lan" not found)`.
- Kernel messages stop at about 120 s. `systemd-journald` restarted at 75 s.
- Hypotheses, unverified:
  - **H1:** nothing is wrong except that `/dev/console` is `tty0` (the last
    `console=`), so systemd's status output goes to VGA, not serial, and we
    cannot see why the getty is missing.
  - **H2:** `dev-ttyAMA0.device` never became ready, and systemd's 90 s
    device timeout expired under slow emulation, so the getty's dependency
    failed.
  - **H3:** a getty runs but its output does not reach the serial port.
- Separately: `lan` was not found. That is the NIC rename under `virt`, a
  separate question (reqs §2.6).

## run3 (diagnosis only: `console=ttyAMA0,115200n8` appended, making serial primary)

One variable changed, observability, to tell H1, H2 and H3 apart.

Result (03:18:29Z to 03:43:35Z): **H2 confirmed**. With serial as the primary
console, systemd's status lines show:

```
[  OK  ] Started Getty on tty1.
[ TIME ] Timed out waiting for device /dev/ttyAMA0.
[DEPEND] Dependency failed for Serial Getty on ttyAMA0.
[FAILED] Failed to start Pre-NixOS setup.
[  OK  ] Reached target Multi-User System.
```

- The serial getty's device job uses systemd's default 90 s device timeout,
  and udev coldplug under TCG emulation finished later than that. So there
  is no serial login, while the VGA getty (tty1) started.
- Real CM4 hardware boots far faster, so this is a VM-test artefact. Fix for
  the VM test only, on the direct-kernel-boot command line:
  `systemd.default_device_timeout_sec=900`.
- **New product finding: pre-nixos.service failed on AArch64.** Its cause
  is to be read from its journal in run4.

## run4: adds `systemd.default_device_timeout_sec=900` (one variable)

Result (03:44:09Z to 03:51:50Z):
- **The serial getty now works.** `nixos login:` appeared at 03:48:49Z, so
  **E5 boot to login takes about 4 min 32 s** under TCG (QEMU started at
  03:44:17Z).
- **The root login failed**: after `root` and an empty password it returned
  to `nixos login:`.
- Root cause, by evaluation:
  - `users.users.root.initialHashedPassword` is `null` (locked) on
    `pre-installer-aarch64` and `""` on the x86 `pre-installer`.
  - The flake used the bare `sd-image-aarch64.nix`, which imports only
    `base.nix`. Hydra's `sd_image` job, i.e. the stock image the user
    tested, is `sd-image-aarch64-installer.nix`, which adds
    `profiles/installation-device.nix` (empty root and `nixos` passwords).
- Fix (0.16.1): base the image on the installer variant. Root and `nixos`
  now evaluate to `""`, and the boot settings, and so the R-P2 check, are
  unchanged.
- The image is rebuilt; run5 follows.

## run5: rebuilt image (installer base), same harness command line as run4

Result (image rebuilt in 554 s; QEMU 04:03:14Z to 04:11:21Z):
- **Logged in as root after 280 s.** `uname -m` = `aarch64`, the kernel
  command line is the stock one, and root is `/dev/vda2` (the SD image's
  root partition).
- **pre-nixos failed on the planner postcondition added for #313:**
  `AssertionError: storage plan has no main/slash (#313): vgs=['main', 'swap']`.
- Cause: the guest's `lsblk` shows `mtdblock0 … ROTA 0 … 128M`, which is
  QEMU virt's flash under MTD block emulation (`drivers/mtd/mtdblock.c:343`,
  `mtd_blkdevs.c:367`). The planner took it for an SSD, made it `main`, and
  `slash` did not fit. The HDD `vdb` became `swap`.
- Fix (0.16.2): `block_names.is_non_candidate_device()` is now the single
  exclusion list (loop, zram, ram, dm, md, fd, sr, mtdblock, eMMC hardware
  areas), used by both the inventory and the existing-storage scan. They
  had already diverged: the inventory missed `zram`. The regression test
  `test_aarch64_virt_guest_plans_main_on_the_real_disk` failed before the
  fix.
- Also seen: `enp0s2` stayed DOWN, and pre-nixos reported "lan not found".
  Not yet analysed; pre-nixos had crashed. To check in run6.

## run6: image at 0.16.2

Result (image rebuilt in 601 s; QEMU 04:23:49Z to 04:33:55Z):
- Logged in after 248 s. Planning now uses only `vdb` (the mtdblock0 fix
  works).
- Cleanup ran on `vdb`, then **disko failed inside the guest**:
  `database or disk is full` (`/nix/var/nix/db/db.sqlite`) and
  `write of 61 bytes: No space left on device`. disko evaluates and builds
  its script at run time, and that needs free space in the store.
- Cause: the virtual SD disk was exactly image-sized (3.96 GiB), so the
  image's "Grow the root partition and filesystem to fill the SD card"
  service had nothing to grow into. A real card is larger (the user's is
  238.8G).
- So this is a test-environment artefact, fixed in the harness: enlarge the
  virtual card (`truncate -s 8G`) before boot.
- Product note: an SD card the size of the image is too small. The minimum
  card size should be recorded in the requirements or a hardware note.
- `enp0s2` stayed DOWN again. It is captured in run7.

## run7: 8G virtual card (one variable); network state captured

Result (QEMU 04:34:39Z to 04:45:53Z): **pre-nixos completes on AArch64.**
- **E5 answered:** boot to root login takes **234 s** under TCG, and
  pre-nixos finishes about 647 s after QEMU starts.
- `df /` shows 7.8G, so the first-boot grow worked.
- `storage-status` is `STATE=applied DETAIL=auto-applied`. On `vdb` it
  created `vdb1` (1G vfat on `/mnt/boot`) and `vdb2` with `main-slash`
  (3G on `/mnt`) and `main-swap`. The SD card (`vda`) was untouched.
- **E6 answered:** `nixos-generate-config --show-hardware-config --root /mnt`
  imports `profiles/qemu-guest.nix` (VM-specific) and sets
  `fileSystems."/"` to `/dev/mapper/main-slash`, `/boot` to vfat by UUID, swap
  to `/dev/mapper/main-swap`, and
  `nixpkgs.hostPlatform = "aarch64-linux"`. That is usable input for plan
  item 8 (the installed bootloader).
- **`main-swap` is 4 MiB**: queue item 11's anomaly, seen on a real run.
- **Network:** `enp0s2` is `off`/`unmanaged`, and pre-nixos reports "lan not
  found". Cause, from `network.configure_lan`: with no root public key
  embedded, it intentionally leaves networking untouched. This image was
  built without `PRE_NIXOS_ROOT_KEY` (metadata: `Embedded root key
  fingerprint: none`). The x86 VM tests always build with a key. So this is
  not an AArch64 fault, but the AArch64 VM test must build with a key.

## Settings the permanent AArch64 VM test needs (all from these runs)

- `qemu-system-aarch64 -M virt -cpu cortex-a72 -smp 2 -m 2048`, direct
  kernel boot from the image's own closure, and `-append` with the image's
  `kernel-params` plus `init=…`.
- Test-only additions: `systemd.default_device_timeout_sec=900` (run3) and,
  for diagnosis, `console=ttyAMA0,115200n8`.
- An 8G virtual card (run6) and an embedded root key.
- Login timeout of at least 600 s (234 s measured); pre-nixos timeout of at
  least 1200 s.
